# フロントエンド_フェーズ0

# フェーズの目的

フェーズ0の frontend は、後続の battle / explore / map 改修で表現が再び分裂しないよう、色、effect、入力、presentation event の基礎を整えます。画面全体の作り直しはフェーズ1以降に回し、このフェーズでは共通部品と回帰防止を優先します。

# 両チーム共通の構想と制約

- 表示層は snapshot / renderState / ViewModel / PresentationRequest を描画する。content 全量や save 内部から未発見情報、報酬、衝突、復元状態を推測しない。
- `content/gameplay/visual-presets`、`hitbox-presets`、`background-presets`、`presentation-cues.json` は現行 content の正本として扱う。
- mission ID、enemy ID、projectile ID を見て renderer に新しい個別分岐を追加しない。
- 色は `tokens.css` と `canvas-palette.ts` の semantic role を正本にする。
- `threatNoise` は被弾、聴取不能、hazard 予兆または active hazard に限定する。
- `reduceFlashing` と `lowFrameRateMode` はすべての新規表現で確認する。

# 棚卸し判断

- App / Presentation 境界は現行コードでかなり実装済み。`App.tsx` から `ExploreScreen`、`BattleScreen`、`TransitionPresentationLayer` へ event が渡っているため、旧 P0 チケットをそのまま再発行しない。
- `MapScreen` と `MiniMap` は ViewModel 入力になっている。content 全量を読んでいる問題ではなく、renderer 分割と palette 化の問題として扱う。
- `BattleCanvas` と `ExploreCanvas` の `components/*` re-export は移行期の shim として残っている。削除はフェーズ3で import 移行後に行う。
- 直接色指定は現行 `apps/web/src` で 1057 件確認できる。フェーズ0で全置換するのではなく、audit と helper を先に作る。

# 進行管理

- FE-0-01 と FE-0-02 は BE-0-02 の docs 正本更新と並行可能。ただし token 名の最終固定は BE-0-02 完了後に行う。
- FE-0-03 はフェーズ1の battle / explore / map 改修で使う前提部品。screen 個別の置換はフェーズ1以降。
- FE-0-04 は backend 依存なしで実行可能。presentation/overlay 中の入力持ち越しを防ぐため、フェーズ1より前に完了する。
- FE-0-05 は現行実装を壊さないための smoke test。旧 App / Presentation チケットの残タスクとして扱う。

# FE-0-01 semantic token と canvas palette helper を整備する

タグ: `[phase:0] [team:frontend] [design-system] [palette] [blocking-for-rendering]`

## 現状確認

- `apps/web/src/render/shared/canvas-palette.ts` は存在するが、`hex`、`rgb`、`rgba` の最小 helper に留まる。
- `base.css`、各 screen CSS、Canvas renderer に直接色指定が残っている。
- 直接色指定は `explore.css`、`ExploreCanvas.tsx`、`menu-equipment.css`、`battle.css`、`explore-map.css` に多い。

## 作業

- `base.css` の互換 token は直接値ではなく `tokens.css` の `--color-*` alias に寄せる。
- `canvas-palette.ts` に少なくとも次を追加する。
  - `hex(role)`
  - `rgba(role, alpha)`
  - `gradientStop(role, alpha)`
  - `resolveGlow(role, intensity)`
- `enemyPrototype` のように design package にない role は、prototype 専用として docs に明記するか、既存 role へ統合する。
- 新規 renderer では palette role から色を引く。直接 `rgba(255, 90, 110, ...)` のような値を増やさない。

## 受け入れ条件

- `tokens.css` と `canvas-palette.ts` の role 対応が明確になる。
- 新規 Canvas effect が palette helper だけで色を表現できる。
- `threatNoise` を通常 hover、常時装飾、普通の強調へ使わない。

# FE-0-04 pointer / mouse 入力の二重処理と持ち越しを整理する

タグ: `[phase:0] [team:frontend] [input] [app] [independent]`

## 現状確認

- `use-magnolia-input.ts` は window に `pointerdown/up` と `mousedown/up` を両方 capture 登録している。
- 1 回の pointer 操作が mouse event も伴う環境では、queued mouse press が二重に入る可能性がある。
- `use-magnolia-frame-loop.ts` は equipment modal 中に return しており、その分岐では `syncButtonEdges` が呼ばれていない。

## 作業

- pointer event を基本経路にし、mouse event は pointer 非対応時の fallback にする。
- `pointerId`、`button`、`timeStamp` を使い、同一入力を dedupe する。
- context menu の右クリック処理が scan / interact と競合しないようにする。
- overlay、transition、equipment modal、map/menu close 時は `syncButtonEdges` を呼び、入力 edge を次画面へ持ち越さない。

## 受け入れ条件

- 1 回の左クリックで interact が 1 回だけ発火する。
- 1 回の右クリックで scan が 1 回だけ発火する。
- overlay や equipment modal 上で押した入力が、閉じた直後の explore 操作として消費されない。
