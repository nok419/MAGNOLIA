# バックエンド_フェーズ2

# フェーズの目的

フェーズ2は、探索、mission beat、menu / equipment / archive の ViewModel を整える段階です。frontend が content や profile を直接読んで表示ロジックを再実装しないよう、session 側で表示用の値を作ります。

# 両チーム共通の構想と制約

- 表示層は snapshot / renderState / ViewModel / PresentationRequest を描画する。content 全量や save 内部から未発見情報、報酬、衝突、復元状態を推測しない。
- `content/gameplay/visual-presets`、`hitbox-presets`、`background-presets`、`presentation-cues.json` は現行 content の正本として扱う。
- mission ID、enemy ID、projectile ID を見て renderer に新しい個別分岐を追加しない。差分は content preset、rendererKind、presentation cue、renderState の公開フィールドに置く。
- 色は `apps/web/src/styles/tokens.css` と `apps/web/src/render/shared/canvas-palette.ts` の semantic role を正本にする。`threatNoise` は被弾、聴取不能、hazard 予兆または active hazard に限定する。
- `reduceFlashing` と `lowFrameRateMode` は新規表現、presentation cue、Canvas cache の受け入れ条件に含める。

# 棚卸し判断

- `ExploreSignalHintViewModel` には `confidence`、`category`、`distanceBand`、`detectedState` があるが、`recorded`、`lastScanAtMs`、`isNewlyIdentified` は不足している。
- `EquipmentPanel` は `content` と `profile` を受け取り、owned/equipped/canPurchase/upgrade 表示を frontend で計算している。
- `ArchivePanel` も raw content と unlock 状態の境界を整理する必要がある。
- mission beat の content はあるが、本文 chunk と敵・hazard・fragment の関連を session event として出す仕組みが弱い。

# 進行管理

- BE-2-01 は FE-2-02 の前提。FE-2-01 の ExploreCanvas 分割は先行可能だが、signal UI 完了判定は BE-2-01 後に行う。
- BE-2-02 は FE-2-05 の前提。frontend が mission ID で cue を分岐する実装は不可。
- BE-2-03 は FE-2-04 の前提。ViewModel が確定するまでは frontend は旧計算を削除しない。
- BE-2-04 は BE-2-03 と並行可能だが、command precondition と ViewModel の表示理由は一致させる。

# BE-2-01 ExploreRenderState / signal hint を識別段階つきに拡張する

タグ: `[phase:2] [team:backend] [explore] [viewmodel] [blocking-for-frontend]`

## 現状確認

- 探索 hint の一部 field は実装済みだが、recorded として map/minimap に残る状態と、scan 時刻・新規識別 flag が不足している。

## 作業

- signal hint の状態を `ghost`、`identified`、`recorded` の3段階に整理する。既存の `hint` を残す場合は意味を docs に明記する。
- `lastScanAtMs`、`isNewlyIdentified`、`detectedState` または `recordState` を追加する。
- 未識別の通信や collectible は正確な座標を公開せず、方角、距離帯、カテゴリだけを返す。
- identified / recorded になったものは map / minimap の ViewModel に残す。

## 受け入れ条件

- 未識別通信の正確な座標が renderState に出ていない。
- scan 後に方角、距離帯、カテゴリ、信号強度が表示できる。
- identified / recorded の状態が save / reload 後も不自然に戻らない。

# BE-2-02 mission beat と本文 chunk を PresentationRequest に接続する

タグ: `[phase:2] [team:backend] [mission] [presentation] [content]`

## 現状確認

- mission の wave や intentTag は存在するが、本文 chunk と敵・hazard・fragment window が session event として十分に結びついていない。

## 作業

- mission content に `beatEvents` を追加するか、既存の `wave.intentTag` を session が PresentationRequest に変換する。
- `mission_good_morning` の tutorial 区間を 0〜7 秒敵なし、7〜17 秒 main、17〜23 秒 melee、23〜30 秒 sub 確認、30〜37 秒被弾ノイズ、37〜44 秒 hazard、44〜55 秒帰還準備として確認する。
- `mission_where_are_you` はカナ、タクミ、ミサキの差を intentTag と timing で出し、82.5〜85 秒付近に保護 cue を出す。
- `mission_evacuation` は公共放送、経路更新失敗、残留者の声、保護膜超過を節として分ける。

## 受け入れ条件

- 各 mission の 10 秒ごとの体験が本文 chunk と対応している。
- 同じ enemy を使っても、intentTag と timing で話者差が出る。
- Web 側 TypeScript に mission 固有分岐が増えない。

# BE-2-03 Equipment / Archive / Menu ViewModel を session selector で作る

タグ: `[phase:2] [team:backend] [viewmodel] [menu] [blocking-for-frontend]`

## 現状確認

- `EquipmentPanel` は content と profile から購入可否、強化コスト、装備状態、masking を計算している。

## 作業

- `EquipmentCatalogViewModel` を追加し、`visibleName`、`visibleDescription`、`masked`、`owned`、`equippedSlot`、`currentLevel`、`maxLevel`、`canPurchase`、`purchaseCost`、`canUpgrade`、`upgradeCost`、`lockedReasonLabel` を持たせる。
- `ArchiveViewModel` を追加し、area、transmission、chunk、metadata の unlock 状態と表示文字列を返す。
- `MenuViewModel` で tab ごとの badge、未読、利用可能操作をまとめる。

## 受け入れ条件

- frontend に価格、level cap、unlock condition、未取得 masking の計算式が残らない。
- command の可否と ViewModel の `can*` 表示が一致する。
- archive の未発見本文や報酬を frontend が raw content から推測できない。

# BE-2-04 command precondition と save normalizer の回帰テストを追加する

タグ: `[phase:2] [team:backend] [persistence] [test]`

## 現状確認

- menu ViewModel 化と探索状態追加により、購入、装備、強化、収集、mission 開始、archive 既読などの状態遷移が増える。

## 作業

- purchase / upgrade / equip / collect / start mission / complete mission / open archive / scan identify の precondition test を追加する。
- save migration / normalizer test に新規 field を追加する。
- invalid command の error reason を ViewModel の `lockedReasonLabel` と対応させる。

## 受け入れ条件

- 旧 save を読み込んでも新規 ViewModel と探索状態が壊れない。
- command 不可の理由が UI と session で一致する。
- 追加した state が reload 後に消えない。
