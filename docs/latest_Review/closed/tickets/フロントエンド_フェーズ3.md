# フロントエンド_フェーズ3

# フェーズの目的

フェーズ3の frontend は、フェーズ1・2で導入した preset 駆動 renderer、shared effect、ViewModel UI を整理し、性能、fixture、import 経路、残った直接色指定を仕上げる段階です。

# 両チーム共通の構想と制約

- 表示層は snapshot / renderState / ViewModel / PresentationRequest を描画する。content 全量や save 内部から未発見情報、報酬、衝突、復元状態を推測しない。
- `content/gameplay/visual-presets`、`hitbox-presets`、`background-presets`、`presentation-cues.json` は現行 content の正本として扱う。
- mission ID、enemy ID、projectile ID を見て renderer に新しい個別分岐を追加しない。差分は content preset、rendererKind、presentation cue、renderState の公開フィールドに置く。
- 色は `apps/web/src/styles/tokens.css` と `apps/web/src/render/shared/canvas-palette.ts` の semantic role を正本にする。`threatNoise` は被弾、聴取不能、hazard 予兆または active hazard に限定する。
- `reduceFlashing` と `lowFrameRateMode` は新規表現、presentation cue、Canvas cache の受け入れ条件に含める。

# 棚卸し判断

- `KeyVisualModal.tsx` は 632 行で、live domain ID を使った fake `BattleRenderState` を手書きしている。
- `components/BattleCanvas.tsx`、`components/ExploreCanvas.tsx`、`components/battle-renderer.ts` は re-export shim として残っている。削除は import 移行後に行う。
- `projectile-trails.ts` は trail preset の入口として十分に機能していない。フェーズ1の projectile renderer 移行後、実装または削除を判断する。
- 直接色指定はフェーズ0・1・2で主要部を減らし、最終 baseline 更新と残件整理はフェーズ3で行う。

# 進行管理

- FE-3-01 は FE-1-02、FE-1-03 の preset 駆動化後に行う。cache key が旧 ID fallback 前提にならないようにする。
- FE-3-02 は BE-1-01 の contract と FE-1-01 の renderer dispatch 完了後に行う。
- FE-3-03 は全 import 移行後に行う。re-export shim は参照が残る間は削除しない。
- FE-3-05 は style audit の baseline 更新と合わせて行う。

# FE-3-01 Canvas renderer の cache と低負荷 mode を整理する

タグ: `[phase:3] [team:frontend] [performance] [canvas]`

## 現状確認

- preset 駆動化後は同じ enemy / projectile / fragment / marker 形状を何度も描く箇所が増える。

## 作業

- enemy / projectile / fragment / marker の Path2D または offscreen cache を検討する。
- cache key は `rendererKind`、`visualPresetId`、palette role、shape parameter、reduceFlashing、lowFrameRateMode を含める。
- lowFrameRateMode では粒子数、trail 長、scanline 密度、hazard noise の更新頻度を下げる。

## 受け入れ条件

- battle と explore の通常ケースで frame drop が減る。
- cache により preset 変更が反映されない問題が起きない。
- lowFrameRateMode でも必要な gameplay 情報が消えない。

# FE-3-02 KeyVisualModal を fixture factory 化する

タグ: `[phase:3] [team:frontend] [fixture] [key-visual]`

## 現状確認

- `KeyVisualModal.tsx` は fake `BattleRenderState` を手書きし、live content の ID に依存している。

## 作業

- `render/battle/fixtures/key-visual-render-state.ts` のような fixture factory を作る。
- fixture は live domain ID を直接前提にせず、必要な preset が存在するかを確認する。
- key visual 専用の表示が必要な場合は、runtime renderer へ特例を入れず fixture 側で state を作る。

## 受け入れ条件

- `KeyVisualModal.tsx` の fake renderState 手書きが大幅に減る。
- content ID 変更時に fixture の検査で問題を発見できる。
- runtime battle renderer に key visual 専用分岐が増えない。

# FE-3-03 re-export shim と stub を整理する

タグ: `[phase:3] [team:frontend] [cleanup] [imports]`

## 現状確認

- renderer 分割後の互換として `components/BattleCanvas.tsx`、`components/ExploreCanvas.tsx`、`components/battle-renderer.ts` が残っている。

## 作業

- すべての import を `apps/web/src/render/*` へ移す。
- 参照がなくなった re-export shim を削除する。
- `projectile-trails.ts` など、実装入口として使うなら実装し、不要なら削除する。

## 受け入れ条件

- import 経路が `components` と `render` に二重化していない。
- shim 削除後も build と smoke test が通る。
- stub が予定のないまま残っていない。

# FE-3-04 title / key visual / transition の表現を shared effect に寄せる

タグ: `[phase:3] [team:frontend] [title] [transition] [effects]`

## 現状確認

- `SignalBackdropCanvas`、`KeyVisualModal`、`TransitionPresentationLayer` は battle / explore / map と同じ effect vocabulary へ完全には寄っていない。

## 作業

- title 背景の波紋、粒子、scanline を `SignalPulse`、`ArtificialGrid`、`ResidualFragment` の組み合わせへ寄せる。
- transition は presentation cue の duration と motion 区間に合わせる。
- key visual は runtime renderer と同じ preset / palette を使う。

## 受け入れ条件

- title、battle、explore、map、transition の表現語彙が揃う。
- key visual が runtime と別の色・粒子規則を持たない。
- `reduceFlashing` true で眩しい点滅が残らない。

# FE-3-05 直接色指定の残件を整理し baseline を更新する

タグ: `[phase:3] [team:frontend] [palette] [audit]`

## 現状確認

- 現行 `apps/web/src` には直接色指定が 1057 件ある。フェーズ3では残件を棚卸しし、許容する例外と削除する直接色を分ける。

## 作業

- `style:audit` の baseline を更新する。
- `tokens.css` と `canvas-palette.ts` 以外の直接色を semantic role へ移す。
- 残す必要がある色は、ファイル名、理由、期間を docs に記録する。
- `base.css` の互換 alias が直接値を持たないことを再確認する。

## 受け入れ条件

- 新規 direct color literal は audit で失敗する。
- 既存の直接色は例外リストに明記されるか、palette / token に移行される。
- `threatNoise` の使い道が hazard、被弾、聴取不能、danger tone に限定される。
