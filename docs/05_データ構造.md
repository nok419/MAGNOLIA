# 05_データ構造

更新日: 2026-05-01

## この文書の目的

この文書では、MAGNOLIA のデータ契約を次の観点で固定します。

- gameplay content に何を置くか。
- session が UI へ渡す snapshot / renderState に何を含めるか。
- save に残す進行結果と、毎回再計算する runtime 状態を分けること。
- 解析率、復元率、通信断片、探索信号、装備効果を混同しないこと。

現行のディレクトリ構成と package 境界は `docs/02_開発体制とディレクトリ構成.md` を正本にします。この文書では、実在する content 配下の構造と、Web 側が実際に参照している公開データを中心に記述します。package 内部の細かなファイル名は、コードマップが必要な場合を除きここでは繰り返しません。

## active / prototype / deprecated の運用

`content/gameplay/content-classification.json` は、runtime の active bundle と authoring 用 content を分ける正本です。

- active
  - 現在の playable slice に入る mission、enemy、bullet pattern、projectile、movement pattern を列挙します。
  - `loadContentBundle()` は active に列挙された mission、enemy、bullet pattern、projectile、movement pattern だけを session へ渡します。
- prototype
  - 将来調整用、または現行 mission から到達しない content を列挙します。
  - validator は参照整合性を確認しますが、active bundle には入れません。
- deprecated
  - save 互換や移行記録のために残す ID を列挙します。
  - ID 変更が必要な場合は `content/gameplay/migrated-id-map.json` に旧 ID、新 ID、save への影響を書きます。

active 化する手順:

1. 対象 JSON を通常の content directory に置きます。
2. `content-classification.json` で対象 ID を `prototype` から `active` へ移します。
3. active mission から辿る enemy、bullet pattern、projectile、movement pattern も同じ変更で active にします。
4. `npm run content:manifest` を実行し、manifest を更新します。
5. `npm run content:validate` を実行します。active mission が prototype / deprecated を参照している場合は失敗します。

## 共有用語

- 解析率
  - ミッション中にノイズ源をどれだけ除去できたかを示す値です。敵撃破による `analysisValue` の累積を `analysisTotal` で割って算出します。
- 復元率
  - 通信本文のうち、ノイズで欠損させずに保持できた割合です。本文表示とアーカイブ開放に使います。
- `heardRanges`
  - プレイヤーが欠損させずに聴取できた時間範囲です。互換性のため save に残します。
- `damageRanges`
  - そのランで聴取不能だった時間範囲です。ラン履歴と結果表示に使います。
- `seededHeardRanges`
  - 再挑戦開始時に、過去の累積進行から battle state へ seed される聴取済み範囲です。今回の被弾で過去のアーカイブ進行を失わないために分けます。
- `TranscriptSpan`
  - 本文チャンク内の復元済み範囲を `chunkId + startRatio/endRatio` で表す正規化スパンです。欠損フラグメント回収や、本文時間を軽微に調整した時の破綻防止に使います。
- 自己修復ポイント
  - 装備購入・強化に使う持続的な通貨です。スコアとは別です。
- 危険度
  - ミッションごとの表示用難度です。全体難易度の設定値とは分けます。

```ts
export type TransmissionMaster = {
```

`metadataUnlockThresholds` は解析率で開く基本情報を管理します。本文の開放は解析率ではなく、聴取・復元側のデータで決めます。

### 通信本文チャンク

実在する置き場: `content/gameplay/transmissions` の `.chunks.json`

```ts
export type TranscriptChunk = {
  chunkId: TranscriptChunkId
  transmissionId: TransmissionId
  previousChunkIds?: TranscriptChunkId[]
  lineId: string
  startMs: number
  endMs: number
  speakerLabel?: string
  text: string
}

export type TranscriptSpan = {
  chunkId: TranscriptChunkId
  startRatio: number
  endRatio: number
}
```

運用ルール:

- 同じ意味のセリフでタイミングや文言だけを微調整する場合は `chunkId` を維持します。
- 意味が変わる、分割・統合する、別の発話に変える場合は新しい `chunkId` を発行します。
- chunk を分割・統合・改名する場合は、新しい chunk の `previousChunkIds` または `content/gameplay/migrated-id-map.json` の `transcriptChunk` migration で旧 ID との対応を残します。
- `startMs` / `endMs` は単調増加を原則にし、同じ chunk 内で時間を重ねません。
- アーカイブ表示では、本文を grapheme 単位に分割し、未復元部分をマスクできます。

保存済み `transcriptSpans` は `chunkId + startRatio/endRatio` で復元範囲を持ちます。本文の長さだけを変える場合は同じ `chunkId` 内で割合を維持します。chunk ID を変える場合、normalizer は `migrated-id-map.json` の対応表を使って旧 chunk の割合を新 chunk へ移します。`segments` を省略した split migration は、旧 chunk を `toChunkIds` の数で等分して扱います。任意の対応が必要な場合は次の形で source / target の割合を指定します。

```json
{
  "kind": "transcriptChunk",
  "transmissionId": "tx_good_morning",
  "fromChunkId": "legacy_chunk_id",
  "toChunkIds": ["chunk_gm_001a", "chunk_gm_002a"],
  "segments": [
    {
      "sourceStartRatio": 0,
      "sourceEndRatio": 0.5,
      "targetChunkId": "chunk_gm_001a",
      "targetStartRatio": 0,
      "targetEndRatio": 1
    }
  ]
}
```

現在の slice では、`mission_evacuation` の本文チャンクは 55.7 秒まで存在し、60 秒ミッションの大半が無字幕になる状態ではありません。

### 戦闘 spawn point

実在する置き場: `content/gameplay/battle-spawn-points`

```ts
export type BattleSpawnPoint = {
  spawnPointId: string
  side: "player" | "noiseSource" | "shared"
  xRatio: number
  yRatio: number
  offsetX: number
  offsetY: number
  authoringLabel: string
  intendedUse: string

```

`xRatio` / `yRatio` は戦闘フィールドに対する比率、`offsetX` / `offsetY` は px 単位の補正です。`MissionMaster.playerSpawnId` は `side=player` または `shared`、`EnemySpawn.spawnPointId` は `side=noiseSource` または `shared` のみ参照できます。画面外から入る spawn point は、戦闘フィールド外 96 px 以内に収めます。

### movement pattern

実在する置き場: `content/gameplay/movement-patterns`

```ts
export type MovementPattern =
  | { movementPatternId: string; patternKind: "linear"; speed: number; driftX?: number; driftY?: number }
  | { movementPatternId: string; patternKind: "sineDrift"; speed: number; wobbleAmplitude: number; wobblePeriodMs: number; driftX?: number; driftY?: number }
  | { movementPatternId: string; patternKind: "pauseThenDrift"; speed: number; pauseAtY: number; pauseMs: number; driftX?: number; driftY?: number }
```

`EnemyArchetype.movementPatternId` が既定 route です。`EnemySpawn.movementPatternId` を指定すると、同じ敵の HP、弾幕、visual preset を保ったまま、その spawn だけ別 route に乗せられます。`behaviorKind` と `behaviorParams` は旧 content の互換用として残します。

### ミッション

実在する置き場: `content/gameplay/missions`

```ts

  hazards: BattlefieldHazardSpec[]
  clearCondition: "surviveUntilEnd"
}

export type EnemyWave = {
  waveId: string
  atMs: number
  intentTag?: string
  entries: EnemySpawn[]
}

export type MissionBeatEvent = {
  beatId: string
  atMs: number
  durationMs: number
  intentTag: string
  transcriptChunkIds: TranscriptChunkId[]
  relatedEnemyIds?: EnemyId[]
  relatedHazardIds?: HazardId[]

export type EnemySpawn = {

  enemyId: EnemyId
  spawnPointId: string

```

`durationMs` は音声そのものの長さではなく、導入余白、本文再生、余韻を含むミッション全体の長さです。

```text
durationMs ≒ audioStartDelayMs + transcript の最終 endMs + outroMs
```

現行 content では、完全一致ではなく 2〜3 秒程度の余韻・演出余白を持っています。

`waveId` はミッション内で一意にし、出現済み判定の正本として使います。`spawnId` はミッション内で一意にし、弾幕位相の主キーとして使います。`seed` は同じ spawnId 内の数値揺らぎ用に残します。`overrides` は `tools/content-validator` と loader が許可した移動パラメータだけを上書きできます。

実在する置き場: `content/gameplay/enemies`, `content/gameplay/bullet-patterns`, `content/gameplay/projectiles`

```ts

```

敵弾は「自機を狙う意思を持つ攻撃」ではなく、通信を乱す可視ノイズとして扱います。旧データ互換のために `aimAtPlayer` のような値を残す場合でも、現行方針では player 方向を基準にしない弾幕を優先します。

`BulletPattern.params` の authoring 用標準キーは、`visualOnly`、`nonColliding`、`safeLaneHint`、`baseAngleDeg`、`rotationDegPerSec`、`phaseOffsetDeg`、`oscillationDeg`、`oscillationMs` です。既存 content の互換キーとして `aimAtPlayer` と `spreadDeg` も検査対象に残しています。`visualOnly` または `nonColliding` の敵弾は runtime で `damage` と `noiseDamage` が 0 になり、自機、バリア、弾消しには干渉しません。

content validator は active mission ごとに危険弾数、演出専用ノイズ数、damage を抑制した演出弾数、dangerLevel に対する最大同時危険弾数を出力します。自機初期位置への即時命中と、dangerLevel を大きく超える密度は失敗として扱います。

projectile visual preset は、軌跡、本体形状、発光を別の値として持ちます。

```ts
export type ProjectileContentVisualPreset = {
  presetId: VisualPresetId
  category: "projectile"
  rendererKind: ProjectileRendererKind
  bodyKind: ProjectileBodyKind
  paletteRole: string
  trailKind?: string
  auraKind?: string
  radiusScale?: number
  glowIntensity?: number
  motionSmear?: number
  accessibilityVariant: string
  description?: string
}
```

`bodyKind` は弾本体の形状を決める値です。`radiusScale` は大きさ、`trailKind` は軌跡だけを表します。大きさや軌跡を変えた結果として本体形状が変わる分岐は置きません。許可値は `packages/contracts/src/content-kinds.ts` と `tools/content-validator/src/content-kinds.ts` を一致させます。

### 装備

実在する置き場: `content/gameplay/equipment`


## 拡張時のルール

### content の値だけで表現できる変更

- ミッションの敵配置、出現時刻、hazard、spawn ごとの route 差し替えは missions を変更します。
- 戦闘開始位置やノイズ源の出現位置は battle-spawn-points を変更します。
- ノイズ源の移動 route は movement-patterns を変更します。
- 敵の HP、解析貢献、既定 route、弾幕参照は enemies を変更します。
- 発射間隔、弾数、角度、回転は bullet-patterns を変更します。
- 弾の速度、寿命、ノイズ量、見た目 ID は projectiles を変更します。
- 装備名、説明、入手経路、強化コスト、強化説明、効果上書き、強化時の変化先は equipment を変更します。
- handler に渡す共通パラメータは equipment/effects を変更します。

### content だけで表現できない変更

1. 型契約を増やします。
2. loader validation を増やします。
3. session runtime / selector / renderState を増やします。
4. Web 側は追加された snapshot / renderState だけを描画します。

mission 固有の例外処理を UI 側 TypeScript に直接増やさないでください。

### 新しい装備を増やす時

1. 装備マスターを追加します。
2. 必要な効果定義を追加します。
3. 既存 handler で足りなければ runtime handler を追加します。
4. UI は `equipmentId` と selector 済み表示情報だけを使います。

### 新しい敵や弾を増やす時

1. 敵、弾幕、弾のマスターを追加します。
2. 必要なら movement pattern、汎用 `behaviorKind`、pattern kind を追加します。
3. 描画差分は visual ID / projectile ID / renderer registry で受けます。
4. mission ID を見た UI 側の例外描画を増やさないでください。

## この構成で防ぎたい問題

### 何が問題か

- 解析率と復元率を同じ値として扱うこと。
- ラン単位の結果とアーカイブ累積進行を混同すること。
- 未識別ノードや未聴取本文を UI が content から直接読んでしまうこと。
- 実在しないファイル名をドキュメントに書き、更新対象を誤らせること。

### なぜ問題か

本作では、敵撃破で開く情報と、被弾せずに聞けた本文が別軸です。また、探索では信号の兆候から通信を見つけるため、未識別の座標や未開放本文を表示層へ渡しすぎると体験と秘匿情報が壊れます。

### どうすべきか

- content は静的定義、session は進行と判定、Web は snapshot / renderState の描画に分けます。
- save には進行結果だけを保存し、runtime 状態は保存しません。
- 実装場所を説明する必要がある場合は、コードマップとして限定的に書きます。
- 将来案は「将来案」と明記し、現行ファイル例のように書きません。

### 改善後にどう変化するか

- アーカイブは再挑戦のたびに自然に埋まり、UI 表示と内部状態が一致します。
- 新しい敵、弾、装備、探索信号を追加する時に変更対象が見つけやすくなります。
- SOLID 最適化に進む前に、ドキュメントと実装の参照ずれを減らせます。
