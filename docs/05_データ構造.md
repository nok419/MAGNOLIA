# 05_データ構造

## この文書の目的
この文書では、実装を始める前に次の 3 点を固定します。
- どのデータをどこに置くか
- どの関数を公開 API として用意するか
- IndexedDB に何を保存するか

この文書の対象は、探索、戦闘、装備、アーカイブ、設定、描画用の見た目定義です。

補足:
- 現行実装で稼働している構成は `docs/02_開発体制とディレクトリ構成.md` を正本にします。
- この文書のうち `content/presentation` と Tiled に関する節は、将来の分離案を含みます。
- 現在の runtime は `packages/persistence/src/defaults.ts` と `content/gameplay/*.json` を使います。

## 共有用語
- 解析率
  - ミッション中にノイズ源をどれだけ除去できたかを示す値です。メタデータ開放に使います。
- 復元率
  - 通信本文のうち、どれだけ欠損させずに保持できたかを示す値です。本文開放に使います。
- 通信
  - 探索画面で接続対象になる単位です。1 通信につき 1 ミッションを持ちます。
- ミッション
  - 通信に接続した後の戦闘単位です。時間、敵配置、字幕進行、解析対象量を持ちます。
- `heardRanges`
  - プレイヤーが欠損させずに確保できた時間範囲です。本文開放はこの配列の累積で決めます。
  - ミッション中に過去の復元済み区間を seed として含む場合があります。
- `damageRanges`
  - 被弾やノイズで欠損した時間範囲です。ラン単位の記録に残します。
- `seededHeardRanges`
  - 再挑戦前にすでに復元済みだった時間範囲です。
  - 今回の被弾で過去ログを失わないため、今回分の復元計算から分けて扱います。
- スコア
  - 1 ラン内のパフォーマンス指標です。解析率・復元率・行動から算出します。消費しません。
- 自己修復ポイント
  - 装備の購入・レベルアップに使う持続的な通貨です。ミッション報酬、マップ収集、敵ドロップで獲得します。
- 危険度
  - ミッションごとの難しさを示す表示用の指標です。`MissionMaster.dangerLevel` で持ちます。

## データの置き場
- `content/gameplay`
  - ルールに関わるマスターデータを置きます。
- `content/gameplay/map-logic`
  - ワールドマップ上のノードに対する意味づけ、開放条件、エリアクラスター情報を置きます。
- `packages/persistence/src/defaults.ts`
  - 現行実装では、visual preset / theme / presentation cue の既定値をここで組み立てます。
  - `content/presentation` への分離は将来の拡張候補です。
- `assets`
  - 画像、音、映像などの固定バイナリを置きます。
- IndexedDB
  - セーブ、設定、アーカイブ進行、ミッション履歴を置きます。
- `packages/persistence/src/load-content-bundle.ts`
  - 現行実装では、明示 import した JSON をここで検証し bundle にまとめます。

## 仮データ投入時の最低条件
本文や最終的なデザインが未確定でも、次の項目は先に埋めます。

- 通信: `transmissionId` `missionId` `areaId` `metadataUnlockThresholds` `transcriptChunkIds`
- 本文チャンク: `chunkId` `startMs` `endMs` `text`
- ミッション: `missionId` `durationMs` `analysisTotal` `dangerLevel` `waves`
- 装備: `equipmentId` `slot` `runtimeHandlerId` `unlockSource` `levelParams`

運用ルール:
- 仮本文は短い placeholder でもよいですが、時間範囲だけは実際の構成に近い粒度で切ります。
- アーカイブ本文は完全に復元できた chunk だけを表示するため、本文チャンクは 1〜4 秒程度を目安に、文や意味の切れ目で分けます。
- 被弾した時間範囲は今回の復元対象から除外します。過去に確保済みの `seededHeardRanges` は失いません。
- 仮説明文は後で差し替えてよいですが、ID と参照関係は変更しない前提で進めます。
- 値が未定でも `undefined` で逃がさず、仮値を入れて validation を通します。

### 4. ミッション
ファイル例: `content/gameplay/missions/<missionId>.json`

```ts
export type MissionMaster = {
  missionId: MissionId
  transmissionId: TransmissionId
  durationMs: number
  scrollSpeed: number
  backgroundPresetId: VisualPresetId
  playerSpawnId: string
  analysisTotal: number
  visibilityConditionId?: string
  startConditionId?: string
  audioStartDelayMs: number           // メッセージ再生開始までの導入余白
  outroMs: number                      // メッセージ終了後の余韻時間
  dangerLevel: number                  // 危険度表示用 (1〜5 程度)
  hearingThresholdOverride?: number    // ミッション固有の聴取閾値（省略時は PlayerShipSpec の値）
  baseSelfRepairPoints: number         // 初回クリア時の基本自己修復ポイント報酬
  repeatDecayRate: number              // 再挑戦時の自己修復ポイント減衰率 (例: 0.2 → 2回目以降は基本の20%)
  waves: EnemyWave[]
  hazards: BattlefieldHazardSpec[]
  clearCondition: "surviveUntilEnd"
}

export type EnemyWave = {
  atMs: number
  entries: EnemySpawn[]
}

export type EnemySpawn = {
  enemyId: EnemyId
  spawnPointId: string
  seed?: number
  overrides?: Record<string, number | string | boolean>
}

export type BattlefieldHazardSpec = {
  hazardId: HazardId
  kind: "magneticDisaster"            // 現行の「磁気災害」。通信ノイズを発生させる広域 hazard
  spawnAtMs: number                    // 予兆開始時刻
  telegraphMs: number                  // 薄い赤点滅の持続時間
  activeMs: number                     // ノイズ走行と接触判定の有効時間
  fadeOutMs: number                    // 消失演出の時間
  tickIntervalMs: number               // 接触中に何 ms ごとにノイズを与えるか
  noiseDamage: number                  // 1 tick あたりのノイズ量
  enemyDamagePerSecond?: number        // active 中に enemy へ与える継続ダメージ
  area: BattlefieldHazardArea
  motion: BattlefieldHazardMotion
  visualPresetId: VisualPresetId
  visibilityConditionId?: string
}

export type BattlefieldHazardArea = {
  shape: "rect"                        // 帯型、上半分、広域矩形をまずこれで表現する
  x: number
  y: number
  width: number
  height: number
}

export type BattlefieldHazardMotion =
  | {
      motionKind: "static"
    }
  | {
      motionKind: "linear"             // マップ外からの飛来は初期座標を画面外に置き、速度で侵入させる
      velocity: Vector2
    }
```

必要な理由:
- 戦闘の長さ、敵出現、解析率の分母を固定するためです。
- `analysisTotal` を明示し、撃破による進行量の算出を単純化するためです。
- `audioStartDelayMs` + 音声長 + `outroMs` = `durationMs` の関係で、ミッション全体のタイムラインを制御します。
- `baseSelfRepairPoints` と `repeatDecayRate` によって、初回クリアに大きな報酬を与えつつ周回での過度な稼ぎを抑えます。
- `hazards` によって、敵弾とは別の広域環境 hazard をミッション固有要素として扱うためです。
- 現行の「磁気災害」のような要素は、汎用システム名を `BattlefieldHazard`、具体 kind を `magneticDisaster`、ゲーム内の呼称を「磁気災害」として扱います。

### 4.5 自機仕様
ファイル例: `content/gameplay/player/ship.json`

```ts
export type PlayerShipSpec = {
  // 戦闘パート
  baseMoveSpeed: number         // 通常移動速度
  focusMoveSpeed: number        // 低速移動（集中）時の速度
  hitboxPresetId: HitboxPresetId  // 当たり判定プリセット
  invincibilityMs: number       // 被弾後の無敵時間
  meleeInvincibilityMs: number  // 近接攻撃直後の無敵時間
  hearingThreshold: number      // この noiseLevel 以上で聴取不可扱い (例: 0.7)
  noiseDecayRate: number        // 1秒あたりのノイズ自然減衰量

  // 探索パート
  baseExploreSpeed: number      // 探索時の基本移動速度
  exploreDashSpeed: number      // ダッシュ時の探索移動速度（装備でダッシュ機能を解放後に使用可能）
}
```

必要な理由:
- 移動速度・当たり判定・無敵時間・ノイズパラメータは STG の基本パラメータであり、コンテンツ側で調整できるようにするためです。
- 探索速度は装備や進行によって増減しうるため、基準値をマスターとして持ちます。
- 音声聴取の閾値とノイズ減衰速度はゲームバランスに直結するため、コードに埋め込まずデータとして管理します。
- 探索時の2段階速度（通常/ダッシュ）を定義し、ダッシュの使用可否は装備効果で制御します。

### 4.6 ミッション実行状態
`MissionState` は `stepBattle` が内部で保持するランタイム状態です。IndexedDB には保存しません。

```ts
export type MissionPhase = "intro" | "playing" | "outro"

export type MissionState = {
  missionId: MissionId
  phase: MissionPhase
  elapsedMs: number                 // ミッション開始からの経過時間
  audioPlaybackMs: number           // 音声再生位置（intro中は進まない）
  noiseState: NoiseState            // 06_音声管理 参照
  heardRanges: TimeRange[]          // 今回のランで聴取できた区間
  damageRanges: TimeRange[]         // 今回のランで欠損した区間
  seededHeardRanges: TimeRange[]    // 過去ランから引き継いだ達成済み区間
  hazards: BattlefieldHazardState[] // 進行中の広域環境 hazard
  destroyedAnalysisValue: number    // 今回のランで撃破した解析貢献の合計
  score: number                     // 現在スコア（リアルタイム加算）
  selfRepairPointsEarned: number    // 今回のランで回収済みの自己修復ポイント
  restorationRate: number           // ランタイムで参照する復元率キャッシュ
  cleared: boolean                  // surviveUntilEnd を満たしたか
}

export type BattlefieldHazardState = {
  hazardId: HazardId
  kind: "magneticDisaster"
  phase: HazardPhase
  phaseProgress: number
  area: BattlefieldHazardArea
  motion: BattlefieldHazardMotion
  tickIntervalMs: number
  noiseDamage: number
  visualPresetId: VisualPresetId
  lastAppliedAtMs?: number
}
```

フェーズ遷移:
1. intro: `elapsedMs < audioStartDelayMs` の間。接続演出後の余白。音声は再生しない
2. playing: 音声が再生中。`heardRanges` / `damageRanges` がフレームごとに積算される。敵は `waves[].atMs` に従って出現する
3. outro: 音声終了後、`outroMs` が経過するまで戦闘が継続する。記録対象の音声はない

`stepBattle` は `phase` が `outro` を越えた時点で `cleared: true` を設定し、呼び出し元がミッション終了処理に遷移します。

必要な理由:
- `finalizeMission` と `seedMissionStateWithReplayProgress` が参照する `MissionState` の中身を明示するためです。
- ミッションのフェーズ遷移を実装者が迷わないように定義するためです。

### 5. 敵
ファイル例: `content/gameplay/enemies/<enemyId>.json`

```ts
export type EnemyArchetype = {
  enemyId: EnemyId
  hp: number
  collisionDamage: number
  analysisValue: number
  behaviorKind: string
  behaviorParams: Record<string, number | string | boolean>
```

必要な理由:
- 新しい敵種を追加する時に、行動と見た目を分離するためです。

- `dropSelfRepairPoints` は撃破時に即加算せず、戦闘中の pickup として落とす表現にも使います。

### 6. 弾幕パターン
ファイル例: `content/gameplay/enemies/patterns/<patternId>.json`

```ts
export type BulletPattern = {
  bulletPatternId: BulletPatternId
  patternKind: string
  projectileId: ProjectileId
  cadenceMs: number
  burstCount: number
  params: Record<string, number | string | boolean>
}
```

必要な理由:
- 敵本体と弾幕を差し替え可能にするためです。
- 同じ敵見た目で、異なる弾幕だけを量産できるようにするためです。

現行の運用方針:
- 敵弾は「自機を積極的に狙う攻撃」ではなく、ノイズ源が空間へ無差別に放射している可視ノイズとして扱います。
- `params` には `baseAngleDeg` `spreadDeg` `oscillationDeg` `oscillationMs` `rotationDegPerSec` などを入れ、下向き基調の扇状・回転状の弾幕を作ります。
- `aimAtPlayer` は旧 data との互換用に残してもよいですが、現行 runtime では基準方向を player から取りません。

### 7.5 ミッション内の敵配置・弾・磁気災害の保存境界
各ミッションの戦闘内容は、次の 3 層に分けて持ちます。

- ミッション固有の時系列
  - `content/gameplay/missions/<missionId>.json`
  - `waves[]` に敵配置、`hazards[]` に磁気災害の時系列を置きます。
- 複数ミッションで再利用する戦闘部品
  - `content/gameplay/enemies/<enemyId>.json`
  - `content/gameplay/enemies/patterns/<patternId>.json`
  - `content/gameplay/enemies/projectiles/<projectileId>.json`
  - 敵機種、弾幕パターン、弾そのものはここに分けて置きます。
- ランタイムだけで持つ進行中状態
  - `MissionState`
  - 進行中の磁気災害、被弾で変動するノイズ、今回のランの聴取区間などをここに持ちます。

保存ルール:
- IndexedDB にはミッション内容そのものを保存しません。
- セーブに保存するのは `ProfileRow` `TransmissionProgressRow` `MissionRunRow` のような進行結果だけです。
- 敵の現在位置、発射済み弾、進行中の磁気災害は、ミッションを抜けた時点で破棄します。

設計上の意図:
- ミッション修正時にセーブ移行が不要になるよう、静的 content とプレイ結果を分離するためです。
- 同じ敵機種や弾を別ミッションで再利用しやすくするためです。
- フロント側は `MissionMaster` と `BattleSnapshot` を見れば描画でき、保存層の事情を意識しなくて済むようにするためです。
- 磁気災害は player へのノイズ付与だけでなく、active 中に敵弾を打ち消し、敵機へも継続ダメージを与える前提で扱います。

### 8. 装備
ファイル例: `content/gameplay/equipment/<equipmentId>.json`

```ts
export type EquipmentMaster = {

  slot: EquipmentSlot
  name: string
  iconId: string
  summary: string
  description: string
  flavorText: string
  active?: {

    stock: number
    inputAction?: string
  }
  runtimeHandlerId?: string
  passiveEffectIds: EffectId[]
  activeEffectIds: EffectId[]
  unlockConditionId?: string
  visibilityConditionId?: string
  unlockSource: EquipmentUnlockSource
  maxLevel: number
  levelParams: EquipmentLevelParams[]
}

export type EquipmentUnlockSource =

  | { kind: "purchase"; selfRepairPointCost: number }
  | { kind: "transmissionReward"; transmissionId: TransmissionId }
  | { kind: "mapPickup"; nodeId: WorldMapNodeId }

export type EquipmentLevelParams = {
  level: number
  selfRepairPointCost: number    // このレベルへの強化に必要な自己修復ポイント
  effectOverrides: Record<string, number>  // EffectSpec.params の上書き値
}
```

- `summary` は取得 popup や簡易一覧向けの 1 行概要です。詳細説明は `description` に置きます。

必要な理由:
- 装備画面の一覧表示と、ゲーム中の効果発動を同じ定義から扱うためです。
- 追加装備を UI とロジックの両方で同じ ID で参照するためです。
- `slot` 自体を装備カテゴリとして使い、`main` `sub` `os` `subsystem` の 4 系統を明確に分けるためです。
- `unlockSource` によって「どのルートで入手できるか」をコンテンツ側で管理し、ロジック側が入手経路を分岐せずに済むようにするためです。
- `levelParams` によって装備ごとの強化コストと効果上書きをデータ定義でき、自己修復ポイントを消費した強化システムをロジック変更なく実現するためです。
- `subsystem` を 2 枠持てるため、個別装備ファイルと効果定義を分離しておく方が、同じ探索補助や防御補助を複数装備から再利用しやすいためです。

現行実装での強化ルール:
- 装備を入手した時点で、その装備のレベルは 1 として扱います。
- `purchase` `mapPickup` `transmissionReward` のどの入手経路でも同じです。
- 新規開始時は、初期OS「破損」を所持かつ装備済みの状態で始まります。
- `破損` は装備管理のための最低限の OS であり、探索HUD、ミニマップ、強度計、情報パネル、全体マップの解放には使いません。これらは `os: magnolia` の可視化フラグで制御します。
- 装備画面自体は開始直後から開けます。最初の進行条件は、チュートリアル報酬の `os: magnolia` へ換装して装備画面を閉じることです。
- レベルアップ command は、現在レベルの次段階だけを購入します。
- `effectOverrides` のキー名は、対応する handler が読む `params` 名と一致させます。
- したがって `cadenceMs` `shotCount` `radius` などのキーは、content 側で勝手に言い換えません。

装備カテゴリごとの管理基準:
- `main`
  - 弾の形、速度、追尾、貫通、連射間隔など、射撃そのものの違いを持ちます。
  - 実挙動は `mainWeapons[runtimeHandlerId]` の handler を正本にします。
  - 装備ファイルは解放条件、強化段階、UI 表示、どの handler を呼ぶかだけを持ちます。
- `sub`
  - ボム、バリア、設置物、時限効果など、発動結果が大きく異なる装備です。
  - 実挙動は `subWeapons[runtimeHandlerId]` の handler を正本にします。
  - 共通化できる小さい数値効果だけを `EffectSpec` に分離します。
- `os`
  - 進行補助や基礎補正など、比較的一貫した常時効果を置くカテゴリです。
  - 小さい共通効果は `EffectSpec` と `passiveHandlers` を優先し、装備固有の大きい処理が必要な場合だけ専用 handler を追加します。
- `subsystem`
  - 探索中、戦闘中、被弾時、時間経過ごとなど、発火契機がばらつく補助効果です。
  - 2 枠同時装備を前提に、効果の合成と衝突解決を考えて設計します。
  - 共通化できる補助効果は `EffectSpec` と `passiveHandlers` で扱い、特殊な契機は subsystem 専用 hook 群へ切り出します。

### 9. 効果定義
ファイル例: `content/gameplay/equipment/effects/<effectId>.json`

```ts
export type EffectSpec = {
  effectId: EffectId
  effectKind:
    | "mainShot"
    | "subArmBurst"
    | "subArmField"
    | "analysisBoost"
    | "noiseGuard"
    | "cooldownModifier"
    | "compass"
    | "mapReveal"
    | "missionReveal"
    | "conditionalVision"
    | "exploreDash"
  runtimeHandlerId?: string
  hookKind?: SubsystemHookKind
  params?: Record<string, number | string | boolean>
}
```

必要な理由:
- 新しい装備効果を registry 追加で増やせるようにするためです。
- 装備と効果を分離し、1 つの効果を複数装備から再利用できるようにするためです。
- `main` `sub` `os` `subsystem` のどのカテゴリからでも同じ効果定義を参照できるようにするためです。
- `subsystem` を 2 枠同時装備した時も、effect 単位で重複適用や stacking を扱いやすくするためです。
- `hookKind` によって、subsystem 固有の発火契機を content 側から明示できるようにするためです。

effect を別ファイルにする理由:
- 装備ファイルは「何を装備できるか」と「どう解放・強化するか」に集中させるためです。
- effect ファイルは「実際にどの handler を呼び、どの数値を渡すか」を共通化するためです。
- 同じ `mapReveal` や `noiseGuard` を複数の `subsystem` から再利用できるため、装備数が増えても重複記述が増えにくくなります。
- 将来、装備テキストや入手経路を変えても effect 側を再利用できるため、コンテンツ更新の差分を小さくしやすいです。

effect に入れるもの / 入れないもの:
- 入れるもの
  - `mapReveal` `noiseGuard` `analysisBoost` のような再利用可能な小さい効果
  - handler に渡す共通パラメータ
  - 複数装備から参照したい補助効果
- 入れないもの
  - 装備固有の大きな挙動全体
  - 個別ボムの一連の処理
  - 個別バリアの生成、維持、破棄まで含む処理
  - 特殊な subsystem の複雑な状態遷移

判断基準:
- 複数装備から再利用したいなら `EffectSpec`
- 1 装備専用で、挙動の流れそのものが違うなら handler

## 将来の Tiled マップ運用案
ワールドマップは `content/maps/world/<mapId>.tmj` を表示と座標の正本にします。
ゲームロジックは `content/gameplay/map-logic/<mapId>.json` に分離します。

Tiled の object layer には最低限次の規約を持たせます。

- レイヤ名
  - `areaBounds`
  - `transmissionNodes`
  - `spawnPoints`
  - `collectiblePoints`
  - `decorations`

- オブジェクトのカスタムプロパティ
  - `nodeId`
  - `kind`
  - `spawnPointId`

方針:
- 座標、地形、装飾、境界は Tiled 側で持ちます。
- 現行の探索は「1 枚の連続マップ」の上で area をクラスターとして扱います。
- `areaId` `transmissionId` `interactionRadius` `unlockConditionId` は sidecar logic 側で持ちます。
- 同じ `nodeId` を Tiled と sidecar logic の両方で参照します。

探索画面で必要なのは座標と意味づけであり、重いロジック値は Tiled に埋め込みません。

必要な理由:
- 装備変更時に、現在装備中の `main` `sub` `os` `subsystem` 2 枠に応じて呼び出し先を差し替えるためです。
- 後から各装備固有の関数を追加しても、呼び出し元の分岐を増やさないためです。

ランタイム管理基準:
- `main` と `sub` は handler 主体です。
  - 装備ごとの差が大きいため、`runtimeHandlerId` を起点に個別関数を呼びます。
  - 実際の差分は handler だけでなく、`projectileId` や `fieldId` を通じて描画側にも渡します。装備を替えても見た目が同じままにならないよう、main / sub の archetype ごとに描画分岐を持ちます。
  - 共通化できる小さな数値だけを `EffectSpec.params` で補助します。
- `os` と `subsystem` は共通効果主体です。
  - まず `passiveHandlers` で扱えるかを検討します。
  - それで足りない時だけ専用 hook を追加します。
- `passiveHandlers` と `subsystemHooks` は、実行時に `source` と `effect` を束縛した closure として解決します。
  - これにより handler は level 反映済みの `effect.params` を直接読めます。
- scene や UI に装備 ID の条件分岐を書きません。
  - 装備差分は `resolveLoadout` と registry 側へ寄せます。
  - ただし battle 描画は `projectileId` `fieldId` の単位で分岐してよく、これは装備差分を画面へ正しく反映するための公開契約として扱います。
- `RuntimeEffectRequest` に入らない表現が必要なら、scene 側に直書きせず request union を拡張します。
  - 例: `triggerBomb` `spawnBarrier` `spawnField` `clearEnemyProjectiles`

subsystem の hook 基準:
- `onExploreStep`
  - 探索中だけ効く補助。例: 視界拡張、マップ補助
- `onBattleStep`
  - 時間経過ごとに効く補助。例: 解析率の継続上昇
- `onPlayerHit`
  - 被弾時に効く補助。例: ノイズ軽減、緊急防御
- `onEnemyDestroyed`
  - 敵撃破時に効く補助。例: 一時的バフ、回収補助
- `onMissionStart` / `onMissionEnd`
  - ミッション全体にかかる補助。例: 初期シールド、報酬補正

公開関数:
- `runSubsystemHooks(input: { bindings: EquipmentRuntimeBindings; context: SubsystemHookContext }): SubsystemHookResult`
  - `analysisDelta` で継続解析を加算します。
  - `noiseDelta` で被弾時のノイズ軽減を返します。
  - `effectRequests` で演出や補助オブジェクト生成を返します。

実装判断の順序:
1. 装備差分が数値と共通効果だけで収まるかを見る
2. 収まるなら `EffectSpec` と既存 handler を使う
3. 収まらないなら `mainWeapons` `subWeapons` `passiveHandlers` へ専用 handler を追加する
4. それでも subsystem の発火契機を表せないなら subsystem hook を追加する

### 15. 報酬計算
```ts
calculateMissionRewards(input: {
  missionState: MissionState
  mission: MissionMaster
  transmission: TransmissionMaster
  previousProgress: TransmissionProgressRow | null
  difficulty: Difficulty
  difficultyModifiers: DifficultyModifiers
}): MissionRewardResult

export type MissionRewardResult = {
  score: number
  selfRepairPointsEarned: number
  isFirstClear: boolean
  newHeardRangeMs: number
}
```

スコアの算出方針:
- 解析率（敵撃破による貢献）と復元率（被弾せずに聴いた割合）の両方を評価する
- 被弾を避けて聴き続けるプレイスタイルも、積極的に敵を倒すプレイスタイルも正当に評価される
- 具体的な計算式は調整段階で決定する

自己修復ポイントの算出方針:
- `baseSelfRepairPoints`（ミッション定義）× 初回/再挑戦倍率 + 敵ドロップ合計 + 新規 heardRanges ボーナス
- 初回クリア: `baseSelfRepairPoints` の 100%
- 再挑戦: `baseSelfRepairPoints * repeatDecayRate`（例: 20%）
- 新規 heardRanges: 過去の累積と比較して新たに聴取できた時間に比例した自己修復ポイントを追加で付与する
- この設計により「同じミッションを繰り返すだけ」では自己修復ポイントがほぼ増えず、「新しいミッションへ挑戦」や「まだ聴けていない区間を埋めに行く」が自然な稼ぎ方になる

### 15.1 難易度修飾子

## 保存しないもの
次の情報は保存しません。
- エリアや装備のマスターデータそのもの
- 見た目の生成済みテクスチャ
- その場で再計算できる派生 ViewModel

理由:
- content 更新と save 更新を分離するためです。
- 壊れた cache を save に残さないためです。

## 拡張時のルール
### 新しい敵種を増やす時
1. `EnemyArchetype` を追加します。
2. 必要な `BulletPattern` `ProjectileSpec` を追加します。
3. `behaviorKind` の handler を registry に登録します。
4. `VisualPreset` を追加します。

### 新しい装備を増やす時
1. `EquipmentMaster` を追加します。
2. `EffectSpec` を追加します。
3. `effectKind` の handler を registry に登録します。
4. UI 用の `iconId` と説明文を追加します。

### 装備をレベルアップ可能にする時
1. `EquipmentMaster.maxLevel` に上限を設定します。
2. `levelParams` に各レベルの `selfRepairPointCost` と `effectOverrides` を追加します。
3. 入手時に `ProfileRow.equipmentLevels[equipmentId] = 1` を入れ、以後の強化で 2, 3... と進めます。
4. `resolveLoadout` 内で `equipmentLevels` に応じた `effectOverrides` を `EffectSpec.params` に適用します。
5. save schema に変更はありません（`equipmentLevels` は既存の `ProfileRow` に含まれます）。

### マップ収集要素を増やす時
1. `CollectibleMapNode` を `WorldMapLogic.collectibleNodes` に追加します。
2. Tiled の `collectiblePoints` レイヤにオブジェクトを配置し、同じ `nodeId` を持たせます。
3. `collectibleKind` に応じて `selfRepairPointAmount` または `equipmentId` を設定します。
4. 必要なら `visibilityConditionId` を設定して、特定条件下でのみ出現させます。
5. `ProfileRow.collectedNodeIds` に取得済みが記録されるため、save schema の変更は不要です。

### 新しい見た目だけを増やす時
1. `content/presentation/visuals` を追加または更新します。
2. `VisualPresetId` の参照先だけを差し替えます。
3. save schema は変更しません。

## この構成で防ぎたい問題
### 何が問題か
- 解析率と復元率を同じ値として扱ってしまうことです。
- ラン単位の結果と、アーカイブの累積進行を混同してしまうことです。
- 装備や敵の追加時に、見た目変更がルール変更を壊すことです。

### なぜ問題か
- 本作は「敵撃破で開く情報」と「被弾せずに聞けた本文」が別軸だからです。
- 通信ログ UI は時間範囲の保存がないと実装できないからです。
- 敵機や弾の見た目を後から増やす設計なので、識別子と handler が曖昧だと拡張時に破綻するからです。

### どうすべきか
- `MissionResult` と `TransmissionProgressRow` を分け、ラン結果と累積進行を別々に持ちます。
- 本文は `heardRanges` の累積で管理します。
- 効果と見た目は ID 参照にし、handler と preset を別ファイルで持ちます。

### 改善後にどう変化するか
- アーカイブは再挑戦のたびに自然に埋まり、UI 表示と内部状態が一致しやすくなります。
- 新しい敵、弾、装備を追加する時に、変更対象が決まった範囲に収まります。
- Claude Code は見た目と画面演出を動かしやすくなり、Codex は保存形式とルール計算を保守しやすくなります。
