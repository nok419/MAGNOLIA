# 04_描画ルール

## 実装方針メモ
現行実装では、探索画面と戦闘画面の描画は Web 表示層の Canvas 2D で行う。
戦闘側は canvas host と描画 renderer が分かれており、探索側も今後の分割対象を含む。正確なファイル単位のコードマップは `02_開発体制とディレクトリ構成` を参照する。

このゲームの自機、敵機、敵弾は、原則として固定PNGではなく、パラメトリックな図形定義から生成する。
ただし、ゲーム中は「毎フレーム図形を再生成」はしない。
初期化時またはスポーン時に図形を生成し、可能ならテクスチャ化してキャッシュし、その後はスプライトとして描画する。

目的は次の3点
- デザイン調整を数値変更で行えるようにする
- 個体差、回転、発光、破損表現を実装しやすくする
- 描画負荷を抑える
推奨構成は「見た目定義」と「実描画」を分離すること。
見た目定義は JSON ないし TypeScript の設定オブジェクトで持ち、描画時はそこから一度だけ生成する。

この段階で先に固定する対象は次の通りです。
- `VisualPreset` の入出力項目
- `HitboxPreset` の形状契約
- `ProjectileSpec` の速度、寿命、trail preset の受け渡し
- `PresentationRequest` の座標、duration、blocking などの payload

逆に、後から調整してよい対象は次の通りです。
- 自機、敵機、敵弾の形状係数
- 色、発光量、グリッチ量
- 軌跡の長さ、フェード、粒子数
- UI パネル、バー、タブの見た目

理由:
- 先に renderer の入力を固定すれば、見た目の試行錯誤を続けてもロジック側を巻き込みにくいためです。
- 最終デザインが固まる前に描画関数を固定すると、装備差分や演出差分を後から入れにくくなるためです。

装備カテゴリごとの描画入力の考え方:
- `main`
  - 弾の見た目は `ProjectileSpec` `VisualPreset` `RuntimeEffectRequest` から組み立てます。
  - main ごとの違いは handler が出す request の差で受けます。
- `sub`
  - ボム、バリア、設置物などは、専用 request を追加して描画側へ渡します。
  - scene 側で装備 ID を見て見た目を分岐しません。
- `os` `subsystem`
  - 常時補助や被弾時補助は、UI 状態、presentation request、selector 済み ViewModel を使って表示します。
  - 装備名から直接効果を推測して描画せず、Codex が返した状態だけを使います。
- 広域環境 hazard
  - `BattleHazardViewModel` と `HazardVisualPreset` から描画します。
  - 予兆中は淡い赤点滅、active 中は領域内のノイズ走行、fade 中は減衰だけを描画します。
  - 接触判定の有無は `phase` に従い、描画側で独自に damage 判定を持ちません。

## 演出の入出力境界
- Codex は `PresentationRequest` の型、発火条件、座標、ブロッキング条件を決める
- Claude Code は `PresentationRequest` と cue 定義を参照して、実際の見た目とタイムラインを組む
- 現在の Web 実装では overlay channel の表示が先行しており、explore / battle / transition channel は今後の演出実装対象を含む
- 描画側は未探索マップの全景、未発見ノード、未聴取本文を直接読まない
- UI パネルや演出の都合で追加情報が必要な場合は、先に contract を増やしてから使う

現時点で演出 request を受ける想定の主な対象は次の通り
- 最初のシステムメッセージ風演出
- チュートリアル前の行動制限と視界制限
- チュートリアルクリア後の制限解除エフェクト
- 2D 空間上の自機移動の軌跡
- 通信接続時の遷移演出
- ワープ時の遷移演出

担当メモ
- 自機と擲弾の形状、パネルとバー、装備タブ、アーカイブタブ、演出の見せ方は Claude Code が主担当
- 解析率、復元率、装備効果、未開放情報の保護、演出発火条件は Codex が主担当

## 描画の基本ルール
- DOM/SVG を大量に並べて動かす構成は避ける
- 現行は Canvas 2D で描画する
- WebGL 系へ移す場合も、まず `renderState` と `PresentationRequest` の契約は維持する
- 図形の生成は初期化時、ステージ開始時、スポーン時のいずれかに限定する
- 毎フレーム更新するのは位置、回転、スケール、アルファ、発光量、フレーム切替だけにする
- ノイズ形状は毎フレーム乱数生成しない。seed 固定で個体ごとに形を決める

### 当たり判定
当たり判定は見た目とは別管理にする
もし PixiJS を使うなら、
Graphics で一度描く → RenderTexture 化 → 以後 Sprite として使う
という流れを基本にする。

## 性能面を担保するための注意
次の実装は避ける：
- 敵弾1発ごとに毎フレームポリゴンを組み直す
- ノイズを毎フレームランダム再生成する
- 円弧を毎フレーム多数の点列で再計算する
- 軌跡を履歴点100個以上で常時持つ

次の実装を基本にする：
- 同じ見た目の個体は同じテクスチャを共有する
- バリエーションは seed とパラメータの差で作る
- 軌跡は履歴方式より、短いアニメーションフレームか簡易パーティクルで表現する
- オブジェクトプールを使い、敵弾の生成破棄を減らす

想定として、
自機 1
敵 10〜50
敵弾 100〜500
くらいなら、毎フレームの形状再構築を避ければ十分現実的。

## 自機の実装指示
自機は「中央本体の三角形」と「左右の翼の三角形」の3パーツで構成する。
座標は正規化座標系で定義し、実サイズはスケールで決める。

### 描画モジュールの所在
自機描画は shared ship renderer に一元化されている。
戦闘 renderer、探索 Canvas、装備画面 UNIT STATUS パネルはいずれも同じ描画入口を使う。
これら以外で自機を描画する場合も、必ず shared renderer の描画関数または hull metrics 計算を経由して silhouette の一貫性を保つこと。

### バリアント (ShipVariant)
`settings.shipVariant` により `"solid" | "art"` を切り替える。
- `solid`: 初期から存在する視認性重視の 3 ピース機体。戦闘中の可読性を最優先。
- `art`: silhouette は solid と完全に一致する。magnolia の花弁を想起させる装飾弧・
  内部フィリグリー・翼端センサー点・コア共鳴弧を加えた多層バージョン。
  装飾は `artDetailStrength` で強度を一律スケールでき、
  戦闘表示では可読性優先で低めに設定する。

バリアントは見た目層のみを切り替える。当たり判定、機体サイズ、角度、弾道等の
ゲーム挙動には一切影響しない。これは renderer と contracts の両方で公約になっており、
将来変更する場合は本ドキュメントと shared ship renderer の公開コメントを同時に更新すること。

### 実装方針
- 基準幅を 1.0 としたローカル座標で各頂点を定義する
- 黄金比は厳密な装飾ではなく、各部の比率決定に使う
- 描画用ポリゴンと当たり判定用ポリゴンを分ける
- 発光レイヤは別スプライトまたは別描画で重ねる
- 被弾時のノイズや砂嵐は本体形状を崩さず、上からエフェクトで被せる

### 比率の初期案
黄金比・適切な余白を活用したミニマリストデザイン
- 本体幅を 1.0 とする
- 本体高さは 1.618
- 翼の長さは 0.618
- 翼の根元位置は本体下辺の左右寄り
- 本体と翼の間の見た目上の間隔は 0.08〜0.12 程度
- 全体の外接枠に対して余白は 0.12〜0.18 程度確保する

### 実装上の注意
まず白一色シルエットで成立させ、その後に発光やグリッチを足す
- 小サイズでも潰れないよう、極端に細い線は使わない
- 自機は常時表示されるため、描き込みより識別性を優先する
一方でリッチ化のためにセンスよく、適切にグリッチや発光エフェクトを足す：
  - 本体の発光
  - 移動時の軌跡
  - 被弾時のグリッチ
  - メインショットの発射エフェクト（控えめに）
  - サブアームのエフェクト

## 自弾

main shotとsub shotの装備によってエフェクトが変化する。装備を作る段階で固有の形状を指定するので、まずは最も一般的なメインショットだけ作る。
拡張性を維持して。



## 敵機1の実装指示
敵機は次の4パーツで構成する。
- 中心の円（塗りつぶし）
- 外周軌道1（円弧）
- 外周軌道2（円弧）
- 外周軌道2上のアイコン
軌道1と軌道2は、中心円を中心に独立して回転できるようにする。
つまり、敵本体コンテナの中に以下を分けて持つ
- center layer
- orbit1 layer
- orbit2 layer
- icon layer
### 実装方針
- 軌道は「完全な円」ではなく、開始角と終了角を持つ円弧として定義する
- 軌道1は一部分のみ描画する
- 「軌道2上のアイコン」周辺は、円弧を意図的に描画しない欠損区間（余白）を持たせる
- 軌道1、軌道2はそれぞれ独立の回転角速度を持つ
- 角速度は親コンテナの回転ではなく、各軌道レイヤの rotation 更新で表現する
- アイコンは orbit2 の子要素ではなく、角度計算で位置を決めてもよい。どちらでも可

### 半径の初期案
- 中心円半径 r = 1.0
- 軌道1半径 = 1.618r
- 軌道2半径 = 2.618r
- 軌道1線幅 = 0.18r〜0.24r
- 軌道2線幅 = 0.12r〜0.18r
アイコンの外接サイズ = 0.55r〜0.7r
### 角度の初期案
- 軌道1描画範囲は 180°〜240°
- 軌道2描画範囲は 360°
- 軌道2のアイコン周辺に 20°〜35° の欠損区間を設ける
### 動作の初期案
- 軌道1はやや速く回転
- 軌道2は遅く回転
- 逆回転設定・慣性のある切り替えも可能にする
- 被弾時は中心円は保ち、軌道の発光だけ揺らす
- 強敵では軌道の数やアイコン種を差し替えられるよう、データ駆動にする
### 重要
敵機の見た目は「中心円＋円弧＋アイコンの構造」が本質なので、PNG化して固定するより、部品生成して動かした方が自然。
ただし毎フレーム円弧の点列を作り直さず、初回生成後は回転だけ更新すること。

## 敵弾
敵弾は「本体」と「軌跡」を分けて設計する。
本体と軌跡は独立に差し替え可能にして、組み合わせでバリエーションを作る。
想定する本体は2系統。
- 菱形を集合させた弾
- ノイズ形状を組み合わせた弾
軌跡は複数種（自然に見える描画ができるだけの種類）を用意する。
- 軌跡A
- 軌跡B
- 軌跡C
- ...
軌跡はフレームアニメーションまたは短寿命パーティクルで表現する。

### 敵弾本体1：菱形集合型
#### 実装方針
- 1つの弾を、3〜7個程度の小さな菱形パーツで構成する
- 中心軸方向に並べるが、完全整列ではなく少しだけずらす
- 前方ほど大きく、後方ほど小さくして流れを出す
- 弾ごとの差は seed で作る
#### 注意
- パーツ数を増やしすぎない
毎フレーム位置だけ動かし、菱形配置は固定
弾速が高いなら回転させず、進行方向に合わせるだけでよい

### 敵弾本体2：ノイズ塊型
#### 実装方針
- 発射時に seed を用いて、2〜4個の不規則ポリゴンまたは塊を生成する
- 形は個体ごとに固定し、毎フレーム再生成しない
- 拡縮やわずかな回転だけ加える
- 見た目がランダムでも、当たり判定は円または小さめの楕円で固定する
#### 注意
- ノイズはランダム再生成ではなく、固定された不規則性として扱う
- 視認性を損なわないよう、シルエットは極端に散らさない

### 敵弾の軌跡
軌跡は次の3つを別実装にする。
軌跡A
- 細い残光
- 直線寄り
- 連続表示
軌跡B
- 断続的な走査線風
- 少し途切れる
- 点滅アニメーション
軌跡C
- 粒子がほどけるような尾
- 短寿命パーティクルを数個出す
- 3〜5フレーム程度で消す
実装方針:
- 軌跡は本体の履歴点を長く保持しない
- 軌跡A/B はあらかじめ短いフレームを数枚作ってループ再生でよい
- 軌跡C だけ簡易パーティクルでもよい
- 弾1発あたりの付随描画要素は最小限にする

### データ構造の指示
各見た目は、少なくとも次のような定義オブジェクトで持てるようにする。
type ShipVisualSpec = {
  bodyWidth: number
  bodyHeight: number
  wingLength: number
  wingOffsetX: number
  wingOffsetY: number
  glowStrength: number
}

type EnemyVisualSpec = {
  coreRadius: number
  orbit1Radius: number
  orbit2Radius: number
  orbit1Width: number
  orbit2Width: number
  orbit1ArcStart: number
  orbit1ArcEnd: number
  orbit2ArcStart: number
  orbit2ArcEnd: number
  orbit1AngularSpeed: number
  orbit2AngularSpeed: number
  iconType: string
  iconAngle: number
  iconGapAngle: number
  glowStrength: number
}

type BulletVisualSpec = {
  bodyType: "diamondCluster" | "noiseCluster"
  trailType: "trailA" | "trailB" | "trailC"
  seed: number
  scale: number
  glowStrength: number
}

これをもとに、初回生成関数を用意する。

createShipTexture(spec)
createEnemyParts(spec)
createBulletTexture(spec)
createTrailEmitter(spec)

### キャッシュの指示
キャッシュ機能が必須。
同じ spec から同じ見た目ができるなら、毎回作り直さずキャッシュする。
spec を文字列キー化してキャッシュ
bullet はバリエーション数を制限し、完全無限生成にしない
たとえば敵弾の seed は数十種程度にとどめる
自機と敵機はステージ開始時に先生成してよい

### 当たり判定の指示
見た目と当たり判定は分離する。
自機は中心寄りの小さな判定
敵機は中心円ベースで判定
敵弾は円か楕円の単純判定
理由は、見た目を凝るほど判定まで複雑にすると調整が難しくなるため。
視覚的な複雑さは演出、判定は簡潔にする。

### アセット運用の指示
固定画像として持つのは次に限定する。
- タイトルロゴ
- 背景ノイズテクスチャ
- UIアイコン
- 大きな演出用の特殊画像
自機、敵機、敵弾の基本形状は原則コード生成で管理する。
ただし、見た目の質感が足りない場合のみ、薄いノイズマスクやグレインテクスチャを重ねる。

### 受け入れ条件
最低限、次を満たすこと。
- 自機はサイズ変更しても形が崩れない
- 敵機の軌道1と軌道2が独立して回転できる
- 敵弾は本体2種、軌跡3種を任意に組み合わせられる
- 同一見た目はキャッシュされる
画面上に弾が多い場面でも、毎フレーム形状再生成をしていない
当たり判定と見た目が分離されている
