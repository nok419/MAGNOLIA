# 04_描画ルール

## 実装方針メモ
現行実装では、探索画面、戦闘画面、マップ画面の描画は React 配下の Canvas 2D で行う。
主な描画入口は次の通りである。

- 探索 canvas host: `apps/web/src/render/explore/ExploreCanvasImpl.tsx`
- 探索描画本体: `apps/web/src/render/explore/*.ts`
- 戦闘 canvas host: `apps/web/src/components/BattleCanvas.tsx`
- 戦闘描画本体: `apps/web/src/render/battle/battle-renderer-impl.ts`
- 戦闘弾描画: `apps/web/src/render/battle/projectile-renderers.ts`
- 戦闘描画 renderer 解決: `apps/web/src/render/battle/renderer-registry.ts`
- マップ canvas host: `apps/web/src/screens/map/MapCanvas.tsx`
- マップ描画本体: `apps/web/src/screens/map/map-canvas-renderer.ts`
- 共通座標変換: `apps/web/src/render/shared/coordinates.ts`

2026-04-28 以降の表示実装では、`docs/11_design_package` の設計規則を反映し、色、背景、粒子、グリッチ、基本エフェクトの正本を `apps/web/src/app` 配下に置く。
新しい描画を追加する場合は、まず次の既存部品で表現できるか確認する。

- `apps/web/src/app/visual-tokens.ts`
  - 色、線幅、余白、motion の役割 token。
  - Canvas と Cascading Style Sheets（CSS）の色名は、単なる色名ではなく `void`、`signal`、`memory`、`danger` のような用途名を使う。
- `apps/web/src/app/visual-seed.ts`
  - `hashString`、`seededUnit`、`seededRange`、`timeBucket` を提供する。
  - 描画中に `Math.random()` を直接呼ばない。
- `apps/web/src/app/effect-primitives.ts`
  - `drawSignalParticleField`、`drawCarrierLineField`、`drawScanPulse`、`drawSoftBloom`、`drawFocusBracket`、`drawMetricMeter`、`drawFragmentGlyph`、`drawResidualTrail`、`drawScreenVeilTransition` の描画入口。
  - タイトル、メニュー、探索、マップ、戦闘背景、画面遷移はこの primitive を共有する。
- `apps/web/src/app/signal-distortion.ts`
  - `drawSignalDistortion` を提供する。
  - hazard、subtitle、archive 欠損、title glitch の正本。
  - 意味は loss、desync、noise に限定し、ストロボや television（TV）static のような個別実装を増やさない。
- `apps/web/src/app/mission-visual-profiles.ts`
  - mission ごとの背景 motif、粒子密度、memory tone を返す。
  - mission 固有のゲームルール分岐ではなく、表示上の profile として扱う。
- `apps/web/src/render/shared/coordinates.ts`
  - world 座標から canvas 座標への変換を共有する。
  - `ExploreCanvasImpl`、`map-canvas-renderer.ts`、`MiniMap.tsx` などで変換式を重複させない。

このゲームの自機、敵機、敵弾は、原則として固定 Portable Network Graphics（PNG）ではなく、パラメトリックな図形定義から生成する。
ただし、ゲーム中は「毎フレーム図形を再生成」はしない。
初期化時またはスポーン時に図形を生成し、可能ならテクスチャ化してキャッシュし、その後はスプライトとして描画する。

目的は次の3点
- デザイン調整を数値変更で行えるようにする
- 個体差、回転、発光、破損表現を実装しやすくする
- 描画負荷を抑える
推奨構成は「見た目定義」と「実描画」を分離すること。
見た目定義は JavaScript Object Notation（JSON）ないし TypeScript の設定オブジェクトで持ち、描画時はそこから一度だけ生成する。

この段階で先に固定する対象は次の通りです。
- `packages/contracts/src/game-types.ts` の `VisualPreset` の入出力項目
- `packages/contracts/src/game-types.ts` の `HitboxPreset` の形状契約
- `packages/contracts/src/game-types.ts` の `ProjectileSpec` の速度、寿命、trail preset の受け渡し
- `packages/contracts/src/presentation-types.ts` の `PresentationRequest` の座標、duration、blocking などの payload

逆に、後から調整してよい対象は次の通りです。
- 自機、敵機、敵弾の形状係数
- 色、発光量、グリッチ量
- 軌跡の長さ、フェード、粒子数
- User Interface（UI）パネル、バー、タブの見た目

理由:
- 先に renderer の入力を固定すれば、見た目の試行錯誤を続けてもロジック側を巻き込みにくいためです。
- 最終デザインが固まる前に描画関数を固定すると、装備差分や演出差分を後から入れにくくなるためです。

装備カテゴリごとの描画入力の考え方:
- `main`
  - 弾の見た目は `packages/contracts/src/game-types.ts` の `ProjectileSpec`、`VisualPreset`、`RuntimeEffectRequest` から組み立てます。
  - main ごとの違いは handler が出す request の差で受けます。
- `sub`
  - ボム、バリア、設置物などは、専用 request を追加して描画側へ渡します。
  - scene 側で装備 identifier（ID）を見て見た目を分岐しません。
- `os` `subsystem`
  - 常時補助や被弾時補助は、UI 状態、presentation request、selector 済み ViewModel を使って表示します。
  - 装備名から直接効果を推測して描画せず、session が返した状態だけを使います。
- 広域環境 hazard
  - session 側は `packages/contracts/src/session-types.ts` の `BattleHazardViewModel` を生成します。
  - Web 側は `packages/game-session/src/runtime-types.ts` の `HazardRenderState` を受け、`apps/web/src/render/battle/hazard-renderer.ts` で描画します。
  - `packages/contracts/src/game-types.ts` の `HazardVisualPreset` は content 契約として維持しますが、現在の Web 表示では `drawSignalDistortion` と visual token role を使います。
  - 予兆、active、fade は `drawSignalDistortion` の severity と phaseAlpha で表現します。
  - ストロボ、TV static、interlace、block corruption、screen tear は hazard 内に個別実装しません。
  - reduced flashing が有効な場合は、速い明滅ではなく静的な欠損 mask と遅い外枠変化に置き換えます。
  - 接触判定の有無は `phase` に従い、描画側で独自に damage 判定を持ちません。
- 画面遷移
  - `apps/web/src/app/App.tsx` は `apps/web/src/components/ModeTransitionLayer.tsx` を常時重ね、screenKey の変化だけを根拠に transition veil を描画します。
  - 遷移表現は `apps/web/src/app/effect-primitives.ts` の `drawScreenVeilTransition` を使い、スクリーンごとのローカル overlay を増やしません。
  - reduced flashing が有効な場合は、移動量と粒子密度を落とし、静的な signal band に近づけます。
- 弾幕の見た目
  - `content/gameplay/bullet-patterns/*.json` の `visualRole` を renderState に渡します。
  - `content/gameplay/visual-presets/bullet_visual_roles.json` が role ごとの視覚設定を定義します。
  - `packages/persistence/src/load-content-bundle.ts` は visual role 定義を content bundle に含めます。
  - `packages/game-session/src/runtime-types.ts` の `ProjectileRenderState` が `visualRole` と `visualRoleSpec` を Web 側へ渡します。
  - `apps/web/src/render/battle/renderer-registry.ts` は projectile ID より先に `role:*` の候補を解決できるため、content 側で見た目の系統を変更できます。
  - `apps/web/src/render/battle/projectile-renderers.ts` は解決済みの role spec と renderer key に基づいて描画します。
  - runtime は `visualRole` を運ぶだけで、描画形状や色を判断しません。

## 演出の入出力境界
- `packages/contracts/src/presentation-types.ts` は `PresentationRequest` の型、座標、duration、blocking、channel を定義する
- `packages/game-session/src/presentation.ts` は presentation request の生成と寿命管理を担う
- `apps/web/src/app/internal/overlay-presentations.ts` は `channel: "overlay"` を overlay queue に反映する
- `apps/web/src/components/PresentationOverlay.tsx` は overlay channel の見た目を描画する
- `apps/web/src/app/explore-presentation.ts` と `apps/web/src/render/explore/timeline.ts` は探索側の reboot、settle、fade の phase を扱う
- `channel: "transition"` のうち画面切替に伴う表示は、現在は `ModeTransitionLayer.tsx` と `drawScreenVeilTransition` が担当する
- 描画側は未探索マップの全景、未発見ノード、未聴取本文を直接読まない
- UI パネルや演出の都合で追加情報が必要な場合は、先に contract を増やしてから使う

現時点で演出 request を受ける想定の主な対象は次の通り
- 最初のシステムメッセージ風演出
- チュートリアル前の行動制限と視界制限
- チュートリアルクリア後の制限解除エフェクト
- 2D（2次元）空間上の自機移動の軌跡
- 通信接続時の遷移演出
- ワープ時の遷移演出

担当メモ
- 自機と弾の形状は `apps/web/src/app/ship-renderer.ts`、`apps/web/src/render/battle/projectile-renderers.ts`、`apps/web/src/render/battle/renderer-registry.ts` を起点に確認する
- パネル、バー、装備タブ、アーカイブタブは `apps/web/src/screens/menu/` と `apps/web/src/components/` を起点に確認する
- 解析率、復元率、装備効果、未開放情報の保護、演出発火条件は `packages/game-session/src/` と `packages/contracts/src/` を起点に確認する

## 描画の基本ルール
- Document Object Model（DOM）/Scalable Vector Graphics（SVG）を大量に並べて動かす構成は避ける
- 現行は Canvas 2D で描画する
- Web Graphics Library（WebGL）系へ移す場合も、まず `renderState` と `PresentationRequest` の契約は維持する
- 図形の生成は初期化時、ステージ開始時、スポーン時のいずれかに限定する
- 毎フレーム更新するのは位置、回転、スケール、アルファ、発光量、フレーム切替だけにする
- ノイズ形状は毎フレーム乱数生成しない。seed 固定で個体ごとに形を決める
- 背景粒子、title 背景、menu 背景、hazard noise は `apps/web/src/app/visual-seed.ts` の seed を使う
- 新しい Canvas 描画で raw color literal を増やさない。必要な色は `apps/web/src/app/visual-tokens.ts` に役割名として追加する

### 当たり判定
当たり判定は見た目とは別管理にする
もし PixiJS を使うなら、
Graphics で一度描く → RenderTexture 化 → 以後 Sprite として使う
という流れを基本にする。

## 性能面を担保するための注意
次の実装は避ける：
- 敵弾1発ごとに毎フレームポリゴンを組み直す
- ノイズを毎フレームランダム再生成する
- 円弧を毎フレーム多数の点列で再計算する
- 軌跡を履歴点100個以上で常時持つ

次の実装を基本にする：
- 同じ見た目の個体は同じテクスチャを共有する
- バリエーションは seed とパラメータの差で作る
- 軌跡は履歴方式より、短いアニメーションフレームか簡易パーティクルで表現する
- オブジェクトプールを使い、敵弾の生成破棄を減らす

想定として、
自機 1
敵 10〜50
敵弾 100〜500
くらいなら、毎フレームの形状再構築を避ければ十分現実的。

## 自機の実装指示
自機は「中央本体の三角形」と「左右の翼の三角形」の3パーツで構成する。
座標は正規化座標系で定義し、実サイズはスケールで決める。

### 描画モジュールの所在
自機描画は `apps/web/src/app/ship-renderer.ts` に一元化されている。
現在の主な呼び出し元は次の通りである。

- 戦闘: `apps/web/src/render/battle/player-renderers.ts`
- 探索: `apps/web/src/render/explore/player.ts`
- reboot 演出: `apps/web/src/render/explore/reboot-construction.ts`
- 装備画面 UNIT STATUS パネル: `apps/web/src/screens/menu/ShipStatusPanel.tsx`

`apps/web/src/components/BattleCanvas.tsx` は canvas host であり、自機描画は `player-renderers.ts` 経由で `drawShip` を呼ぶ。
`ExploreCanvasImpl.tsx` も canvas host であり、自機描画は `render/explore/player.ts` 経由で `drawShip` を呼ぶ。
これら以外で自機を描画する場合も、必ず `drawShip` または `computeHullMetrics` を経由して silhouette の一貫性を保つこと。

### バリアント (ShipVariant)
`settings.shipVariant` により `"solid" | "art"` を切り替える。
- `solid`: 初期から存在する視認性重視の 3 ピース機体。戦闘中の可読性を最優先。
- `art`: silhouette は solid と完全に一致する。magnolia の花弁を想起させる装飾弧・
  内部フィリグリー・翼端センサー点・コア共鳴弧を加えた多層バージョン。
  装飾は `artDetailStrength` で強度を一律スケールでき、
  `apps/web/src/render/battle/player-renderers.ts` は戦闘中の可読性優先で 0.55 に設定している。

バリアントは見た目層のみを切り替える。当たり判定、機体サイズ、角度、弾道等の
ゲーム挙動には一切影響しない。これは renderer と contracts の両方で公約になっており、
将来変更する場合は本ドキュメントと `apps/web/src/app/ship-renderer.ts` のコメントまたは型を同時に更新すること。

### 実装方針
- 基準幅を 1.0 としたローカル座標で各頂点を定義する
- 黄金比は厳密な装飾ではなく、各部の比率決定に使う
- 描画用ポリゴンと当たり判定用ポリゴンを分ける
- 発光レイヤは別スプライトまたは別描画で重ねる
- 被弾時のノイズや砂嵐は本体形状を崩さず、上からエフェクトで被せる

### 比率の初期案
黄金比・適切な余白を活用したミニマリストデザイン
- 本体幅を 1.0 とする
- 本体高さは 1.618
- 翼の長さは 0.618
- 翼の根元位置は本体下辺の左右寄り
- 本体と翼の間の見た目上の間隔は 0.08〜0.12 程度
- 全体の外接枠に対して余白は 0.12〜0.18 程度確保する

### 実装上の注意
まず白一色シルエットで成立させ、その後に発光やグリッチを足す
- 小サイズでも潰れないよう、極端に細い線は使わない
- 自機は常時表示されるため、描き込みより識別性を優先する
一方でリッチ化のためにセンスよく、適切にグリッチや発光エフェクトを足す：
  - 本体の発光
  - 移動時の軌跡
  - 被弾時のグリッチ
  - メインショットの発射エフェクト（控えめに）
  - サブアームのエフェクト

## 自弾

main shotとsub shotの装備によってエフェクトが変化する。装備を作る段階で固有の形状を指定するので、まずは最も一般的なメインショットだけ作る。
拡張性を維持して。



## 敵機1の実装指示
敵機は次の4パーツで構成する。
- 中心の円（塗りつぶし）
- 外周軌道1（円弧）
- 外周軌道2（円弧）
- 外周軌道2上のアイコン
軌道1と軌道2は、中心円を中心に独立して回転できるようにする。
つまり、敵本体コンテナの中に以下を分けて持つ
- center layer
- orbit1 layer
- orbit2 layer
- icon layer
### 実装方針
- 軌道は「完全な円」ではなく、開始角と終了角を持つ円弧として定義する
- 軌道1は一部分のみ描画する
- 「軌道2上のアイコン」周辺は、円弧を意図的に描画しない欠損区間（余白）を持たせる
- 軌道1、軌道2はそれぞれ独立の回転角速度を持つ
- 角速度は親コンテナの回転ではなく、各軌道レイヤの rotation 更新で表現する
- アイコンは orbit2 の子要素ではなく、角度計算で位置を決めてもよい。どちらでも可

### 半径の初期案
- 中心円半径 r = 1.0
- 軌道1半径 = 1.618r
- 軌道2半径 = 2.618r
- 軌道1線幅 = 0.18r〜0.24r
- 軌道2線幅 = 0.12r〜0.18r
アイコンの外接サイズ = 0.55r〜0.7r
### 角度の初期案
- 軌道1描画範囲は 180°〜240°
- 軌道2描画範囲は 360°
- 軌道2のアイコン周辺に 20°〜35° の欠損区間を設ける
### 動作の初期案
- 軌道1はやや速く回転
- 軌道2は遅く回転
- 逆回転設定・慣性のある切り替えも可能にする
- 被弾時は中心円は保ち、軌道の発光だけ揺らす
- 強敵では軌道の数やアイコン種を差し替えられるよう、データ駆動にする
### 重要
敵機の見た目は「中心円＋円弧＋アイコンの構造」が本質なので、PNG化して固定するより、部品生成して動かした方が自然。
ただし毎フレーム円弧の点列を作り直さず、初回生成後は回転だけ更新すること。

## 敵弾
敵弾は「本体」と「軌跡」を分けて設計する。
本体と軌跡は独立に差し替え可能にして、組み合わせでバリエーションを作る。
想定する本体は2系統。
- 菱形を集合させた弾
- ノイズ形状を組み合わせた弾
軌跡は複数種（自然に見える描画ができるだけの種類）を用意する。
- 軌跡A
- 軌跡B
- 軌跡C
- ...
軌跡はフレームアニメーションまたは短寿命パーティクルで表現する。

### 敵弾本体1：菱形集合型
#### 実装方針
- 1つの弾を、3〜7個程度の小さな菱形パーツで構成する
- 中心軸方向に並べるが、完全整列ではなく少しだけずらす
- 前方ほど大きく、後方ほど小さくして流れを出す
- 弾ごとの差は seed で作る
#### 注意
- パーツ数を増やしすぎない
毎フレーム位置だけ動かし、菱形配置は固定
弾速が高いなら回転させず、進行方向に合わせるだけでよい

### 敵弾本体2：ノイズ塊型
#### 実装方針
- 発射時に seed を用いて、2〜4個の不規則ポリゴンまたは塊を生成する
- 形は個体ごとに固定し、毎フレーム再生成しない
- 拡縮やわずかな回転だけ加える
- 見た目がランダムでも、当たり判定は円または小さめの楕円で固定する
#### 注意
- ノイズはランダム再生成ではなく、固定された不規則性として扱う
- 視認性を損なわないよう、シルエットは極端に散らさない

### 敵弾の軌跡
軌跡は次の3つを別実装にする。
軌跡A
- 細い残光
- 直線寄り
- 連続表示
軌跡B
- 断続的な走査線風
- 少し途切れる
- 点滅アニメーション
軌跡C
- 粒子がほどけるような尾
- 短寿命パーティクルを数個出す
- 3〜5フレーム程度で消す
実装方針:
- 軌跡は本体の履歴点を長く保持しない
- 軌跡A/B はあらかじめ短いフレームを数枚作ってループ再生でよい
- 軌跡C だけ簡易パーティクルでもよい
- 弾1発あたりの付随描画要素は最小限にする

### データ構造の指示

createShipTexture(spec)
createEnemyParts(spec)
createBulletTexture(spec)
createTrailEmitter(spec)

### キャッシュの指示
キャッシュ機能が必須。
同じ spec から同じ見た目ができるなら、毎回作り直さずキャッシュする。
spec を文字列キー化してキャッシュ
bullet はバリエーション数を制限し、完全無限生成にしない
たとえば敵弾の seed は数十種程度にとどめる
自機と敵機はステージ開始時に先生成してよい

### 当たり判定の指示
見た目と当たり判定は分離する。
自機は中心寄りの小さな判定
敵機は中心円ベースで判定
敵弾は円か楕円の単純判定
理由は、見た目を凝るほど判定まで複雑にすると調整が難しくなるため。
視覚的な複雑さは演出、判定は簡潔にする。

### アセット運用の指示
固定画像として持つのは次に限定する。
- タイトルロゴ
- 背景ノイズテクスチャ
- UIアイコン
- 大きな演出用の特殊画像
自機、敵機、敵弾の基本形状は原則コード生成で管理する。
ただし、見た目の質感が足りない場合のみ、薄いノイズマスクやグレインテクスチャを重ねる。

### 受け入れ条件
最低限、次を満たすこと。
- 自機はサイズ変更しても形が崩れない
- 敵機の軌道1と軌道2が独立して回転できる
- 敵弾は本体2種、軌跡3種を任意に組み合わせられる
- 同一見た目はキャッシュされる
画面上に弾が多い場面でも、毎フレーム形状再生成をしていない
当たり判定と見た目が分離されている
